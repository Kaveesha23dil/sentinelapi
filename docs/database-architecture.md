# PostgreSQL monitoring persistence

This Step 4 foundation is separate from DemoCommerce business data. It stores
validated monitoring records; it does not collect WSO2 telemetry, run detections,
populate aggregates automatically or expose a new HTTP API. Step 3.3 still has
unresolved backend-isolation and observed-rate-limiting checks.

## Deployment and connection lifecycle

`compose.yaml` adds PostgreSQL `17.11-bookworm`, a named volume
`sentinelapi_sentinelapi-postgres-data`, and an internal Docker network
`sentinelapi_database-network`. No host binding is configured for 5432. The
unrelated existing PostgreSQL container and WSO2 storage are untouched.
[PostgreSQL's version policy](https://www.postgresql.org/support/versioning/)
lists 17 as supported through November 2029. The minor version is explicitly
pinned; plan deliberate patch updates and backups rather than automatic upgrades.

DemoCommerce and WSO2 remain on `sentinelapi-network`; they are not attached to
the new private database network. The `persistence` tools-profile service joins
only the database network and waits for `postgres` to be healthy. `pg_isready`
is a readiness signal; actual authenticated SQL tests supply connection proof.
The runner uses Python 3.12, SQLAlchemy 2, psycopg 3 and Alembic. It runs as a
non-root user and publishes no HTTP endpoint. Synchronous SQLAlchemy is deliberate
for this batch foundation. A future FastAPI caller must use synchronous routes
or a thread pool; never block an async event loop with these sessions.

The engine uses connection pre-ping, a connection timeout, UTC session timezone,
hidden SQL parameters and disabled SQL echo. Each `transaction()` opens a session,
commits on success and rolls back/closes on failure. Database exceptions are
translated into a safe `PersistenceError` without driver details. Repository
methods flush but do not commit; the caller controls the unit of work.

## Schema and relationships

All seven tables use UUID primary keys generated by the application. All
timestamps use PostgreSQL TIMESTAMPTZ. Validation converts event timestamps to
UTC; sessions render stored instants in UTC. Created timestamps default to now().

| Table | Integrity and query design |
| --- | --- |
| api_services | Unique name/version and optional gateway API ID; referenced service deletion restricted |
| traffic_events | Service FK, unique event_id for deduplication, status 100–599, known HTTP methods, finite nonnegative latency; indexes on API/time, time, status/time |
| traffic_aggregates | Unique API/window; end after start, nonnegative counts and latency, total errors no greater than requests |
| detection_rules | Unique name, object JSONB configuration; enabled defaults true; updated_at maintained by ORM updates |
| security_alerts | API/rule FKs; optional rule set null on deletion; severity/status enums, risk 0–100, ordered detection times; API/time, status/severity and rule indexes |
| alert_evidence | Alert FK cascades on alert deletion; optional public traffic_events.event_id FK set null if event removed; both FKs indexed; object JSONB details |
| audit_logs | Timestamp and entity indexes; object JSONB database column metadata maps to Python metadata_ to avoid SQLAlchemy's reserved metadata attribute |

No retention deletion jobs exist. Cascade/SET NULL behavior is schema behavior,
not permission to delete production records. Cross-API alert evidence is rejected
by the repository. This semantic guard is not a composite database FK; direct
privileged SQL can bypass it. Foreign keys and checks enforce structural integrity.
No cross-API identity or gateway telemetry authenticity is inferred from stored IDs.

`add_event()` uses PostgreSQL ON CONFLICT on event_id. An identical retry returns
the existing row with created=false. Different contents with the same event UUID
raise DuplicateEventConflict; existing data is never overwritten. Queries require
an aware ordered half-open time interval, API ID and a bounded limit (1–1000).

## Validation and data minimization

Event DTOs forbid unknown fields, require aware timestamps and finite latency,
allow only route paths/templates without query strings or fragments and require
`demo:` identifiers or `hmac:` plus 64 hex digits. HMAC calculation and key
management are future collector work. Callers must supply normalized endpoint
templates rather than user-specific URL paths. No request bodies, headers,
passwords or bearer tokens are accepted as event fields.

Current alert/evidence repository DTOs intentionally allow only controlled,
explicitly fabricated demo content. Generic JSONB configuration/audit storage is
internal, not an ingestion API; future writers require field allowlists and
redaction validation before real data is accepted. Database JSONB itself cannot
recognize every possible secret. ORM objects are internal persistence objects,
not a replacement for validating external input.

Credentials come from ignored `.env` or runtime environment. `.env.example`
contains a rejected placeholder, not a usable credential. SQLAlchemy URL.create
handles special characters without interpolating a password into config files.
Never run `docker compose config` without `--quiet` in captured evidence: expanded
output contains secrets. Docker administrators can inspect container environments.
The local bootstrap owner is privileged and can create disposable test databases;
before a real runtime service is introduced, provision separate least-privilege
runtime and migration roles. Internal Docker HTTP/database networking and a
named volume are not encryption or backups. TLS, backup/restore validation,
retention, role separation and audit immutability remain production work.

## Migrations and safe test workflow

The generated and reviewed initial revision is `4061c4c0ee19`. It uses explicit
create-table/index operations; upgrades do not call ORM create_all. The model is
not imported by the migration, so historical revisions remain independent.
Creation order respects FKs; downgrade reverses dependencies. Downgrade code
refuses databases outside the disposable `sentinelapi_test_` namespace.
Alembic reads the engine from runtime settings; no credential-bearing URL is
stored in alembic.ini. See [Alembic's autogeneration guidance](https://alembic.sqlalchemy.org/en/latest/autogenerate.html)
for review requirements and drift checks.

```powershell
# Set a randomly generated POSTGRES_PASSWORD in your ignored .env first.
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify_database.ps1
```

The script builds the tools image, starts only postgres with `--no-recreate`,
applies upgrade head twice and runs alembic check. It creates a uniquely named
disposable test database, runs upgrade twice, downgrade/base and upgrade, then
all database/validation tests. Ordinary integration tests use rollback isolation;
only labeled persistence checks commit fabricated records in that test database.
A marker is read by a new application process after restarting only PostgreSQL.
`-SkipRestart` explicitly leaves that check pending. It never runs compose down,
deletes a volume, or downgrades the main database. A failed run overwrites old
success evidence with an incomplete report. Test databases are retained for
inspection; cleanup is a separate deliberate administrative action.

For future schema changes, generate against a disposable schema, review every
operation, test downgrade there, back up and apply only reviewed upgrades to the
project database. Never use downgrade to reset real project data. Take backups
outside the repository; database files, dumps, volumes and secrets are ignored.
